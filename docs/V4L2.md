This document answers the Rule 25 question "How does V4L2 work?" for PACSCORDER. It covers:

- which device nodes PACSCORDER uses on each platform;
- which ioctls go to which node, and in which order;
- how the TC358743 is brought from "driver probed" to "frames streaming".

It covers the stretch between the TC358743 driver and the encoder in the mandated pipeline: `TC358743 → CSI-2 → Raspberry Pi CSI-2 receiver → Media Controller → V4L2 → DMABUF → Encoder` (REQ-ARCH-001).

## 2. Scope and governing decisions

- **ADR-001 (ACCEPTED).** Capture goes through kernel V4L2 and the Media Controller, not through direct access to CSI hardware from userspace. REQ-DRV-001 (DRAFT) also says userspace shall not access TC358743 or receiver registers directly.
- **ADR-006 (PROPOSED).** Use Media Controller mode on all four platforms and control the TC358743 only through its sub-device node. One application and one procedure would then serve every platform. Until the owner accepts it, the legacy mode on Pi 4/CM4 (section 5) remains a documented alternative.
- **ADR-005 (PROPOSED).** Default media bus code `MEDIA_BUS_FMT_UYVY8_1X16`.
- **ADR-007 (OPEN).** Whether the capture side is GStreamer, FFmpeg or a direct V4L2 application is not decided. This document describes the kernel interface each of them would have to drive.
- **HDMI audio (REQ-CAP-006, DRAFT; required by the owner on 2026-10-07, OQ-004 ANSWERED).** *(Added 2026-10-08.)* The audio samples do not pass through V4L2: they travel on I2S to an ALSA card ([DEVICE_TREE.md](DEVICE_TREE.md) §3.5). V4L2 is still involved twice: the TC358743's audio controls and their change events (sections 9 and 11), and the video buffer timestamps that audio has to be aligned with (section 12.1).
- **Live latency (REQ-STR-002, DRAFT; owner decision of 2026-10-08, OQ-116 ANSWERED).** *(Added 2026-10-09; research topic K / OQ-116.)* Under 1 second camera-to-viewer, for WebRTC viewers only; RTMP outputs are best-effort. Capture through V4L2 is one term of that budget: section 12.2 gives the capture-side facts, and the full budget is in [PERFORMANCE.md](PERFORMANCE.md) (latency budget section). Nothing has been measured (OQ-125).

## 4. Media graphs per platform

**Pi 4 / CM4, Unicam in Media Controller mode** (selected by the overlay's `media-controller` parameter [C-10], [B-43]; PROPOSED by ADR-006):

```text
"tc358743 <bus>-000f" pad 0 (source) ──[IMMUTABLE | ENABLED]──► "unicam-image"  (/dev/videoN)
```

There is no receiver sub-device and no link to configure [C-36]. Reasoning: formats are therefore set on the TC358743 pad and on the video node; no source gives a tested Pi 4 Media Controller sequence (NEEDS VERIFICATION, TEST-PLT-001; see section 6 notes).

**Pi 5 / CM5, RP1 CFE (always Media Controller):**

```text
"tc358743 1x-000f" pad 0 ──[IMMUTABLE | ENABLED]──► "csi2" pad 0 (sink)
"csi2" pad 4 (source)    ──[flags 0 = disabled; userspace must enable]──► "rp1-cfe-csi2_ch0"  (/dev/videoN)
"csi2" source pads       ──[disabled]──► other "rp1-cfe-<node>" video nodes, "pisp-fe"
```

Sensor-to-csi2 links are created `IMMUTABLE | ENABLED`; csi2-to-video-node links are created disabled. To write raw frames to memory, userspace must enable `"csi2":4 -> "rp1-cfe-csi2_ch0":0` [C-32], [C-33].

**Pi 4 / CM4, legacy video-node mode** (overlay default): the video node is the control point and the sub-device nodes are read-only [C-36], [B-25]. The register does not describe the entity and node names in this mode: NEEDS VERIFICATION (TEST-PLT-001).

## 5. Legacy video-node mode vs Media Controller mode

| | Pi 4 / CM4 — legacy (overlay default) | Pi 4 / CM4 — Media Controller (`media-controller` parameter) | Pi 5 / CM5 |
|---|---|---|---|
| How it is selected | The `tc358743` overlay's fragment@100 sets the csi1 compatible to `"brcm,bcm2835-unicam-legacy"` [C-10], [B-43] | The `media-controller` parameter removes fragment@100, leaving `"brcm,bcm2835-unicam"`, which forces Media Controller mode [C-10], [B-43], [E-40] | `dtoverlay=tc358743` is redirected to `tc358743-pi5`, which has no legacy fragment and no `media-controller` parameter [C-11], [E-43], [G-13] |
| EDID and DV-timings ioctls | On `/dev/videoN`; Unicam forwards `S_EDID`/`G_EDID`, `S`/`G`/`QUERY`/`ENUM_DV_TIMINGS` and `DV_TIMINGS_CAP` to the sub-device [B-25], [C-36] | Not on the video node; issue them on `/dev/v4l-subdevN` [B-25], [C-36] | On `/dev/v4l-subdevN`; the CFE driver has no EDID or DV-timings handling [B-25] |
| Sub-device nodes | Registered read-only [C-36] | Registered read-write [C-36] | Used read-write in the reported sequence [C-33] |
| Setting the format | `VIDIOC_S_FMT` on the video node changes only the pixel format; timings come from DV timings [C-37] | Sub-device pad format plus video-node format (reasoning by analogy with [C-33]; NEEDS VERIFICATION) | Pad formats through the Media Controller plus video-node format [C-33]. A Raspberry Pi engineer reported that `VIDIOC_S_FMT` alone does not set the resolution on Pi 5 [C-41]. |
| Links | — | One immutable, enabled link [C-36] | `csi2:4 → rp1-cfe-csi2_ch0` must be enabled [C-32] |
| Official Raspberry Pi TC358743 documentation | Yes: the only official TC358743 text, in the Unicam section [C-37], [C-38] | No mode-specific example (reasoning from [C-38]) | None [C-38]; community-reported sequence [C-33] |

Further detail on legacy mode (*research gap*, topic B): on the read-only sub-device node, `VIDIOC_SUBDEV_S_DV_TIMINGS` and ACTIVE `S_FMT` return `-EPERM`, while `S_EDID` is not blocked. Reasoning: mixing the two nodes in legacy mode is therefore not a safe way to get one code path.

**ADR-006 (PROPOSED)** proposes the middle and right-hand columns: Media Controller mode everywhere, so EDID, DV timings, events and pad formats always go through `/dev/v4l-subdevN`. The alternative is legacy mode on Pi 4/CM4. It matches the official example [C-37], but it would need a second control path and test matrix. The decision is the owner's (OQ-014).

## 6. Bring-up control sequence (PROPOSED — ADR-006)

**Status: PROPOSED, NOT STARTED. NOT YET RUN ON PACSCORDER HARDWARE.** Every step is derived from the cited sources. The sequence serves REQ-CAP-002, REQ-CAP-003 and REQ-CAP-004.

**Preconditions:**

- the overlay is loaded in Media Controller mode ([DEVICE_TREE.md](DEVICE_TREE.md)); only `dtoverlay=tc358743,<param>=<val>` is attested as `config.txt` syntax [G-12], so writing the `media-controller` parameter as a bare word is NEEDS VERIFICATION (OQ-100);
- the driver has probed (TEST-DRV-001);
- nodes have been discovered (section 3).

| # | Step | Node | Interface | Behaviour | Errors / caveats | Facts |
|---|---|---|---|---|---|---|
| 1 | Write the project EDID | sub-device | `VIDIOC_SUBDEV_S_EDID`, pad 0, `start_block` 0, at most 8 blocks | Driver drops HPD, writes EDID RAM, then raises HPD after `HZ/7` (140 ms at `HZ=250`) if source +5V is present | `-EINVAL` (pad or `start_block` ≠ 0); `-E2BIG` (> 8 blocks). Until this is done the driver does not raise HPD, so a source sees no sink. | [A-32], [B-22], [B-21], [A-33] |
| 2 | Subscribe to events | sub-device | `V4L2_EVENT_SOURCE_CHANGE`; `V4L2_EVENT_CTRL` | Source-change event is sent on sync or DE change when a sub-device node exists. *(Added 2026-10-08.)* `V4L2_EVENT_CTRL` on the "Audio sampling rate" control reports HDMI audio rate changes (section 9) | On Pi 5/CM5 the event is reported not to reach the video node (section 9) | [B-38], [B-39], [B-18], [C-42]; [I-21] |
| 3 | Wait for a signal | sub-device | Event, or repeat step 4 until it returns 0; control `V4L2_CID_DV_RX_POWER_PRESENT` | Without a wired INT the driver polls every 1000 ms | Detection latency up to about 1 s (reasoning; RISK-013) | [A-30], [B-19], [B-16] |
| 4 | Query timings | sub-device | `QUERY_DV_TIMINGS` | Returns timings derived from chip registers; fps is an integer | `-ENOLINK` (HPD low / no TMDS), `-ENOLCK` (no stable sync), `-ERANGE` (outside capability, e.g. interlaced — reasoning [B-27]) → REQ-CAP-005 | [B-29], [B-28] |
| 5 | Apply timings | sub-device | `S_DV_TIMINGS` with the queried timings | Stores timings, mutes the stream, reprograms PLL and CSI, recomputes the lane count. Identical timings → no action. | `-ERANGE`; does not check lanes against DT `data-lanes` | [B-30], [B-31] |
| 6 | Pi 5 / CM5 only: enable the link | media device | `"csi2":4 -> "rp1-cfe-csi2_ch0":0 [1]` | Enables the disabled csi2 → video-node link | — | [C-32], [C-33] |
| 7 | Set pad formats | sub-device / media device | `tc358743:0` media bus code (UYVY8_1X16 per ADR-005, PROPOSED), size equal to the timings, `field:none`, colorspace; on Pi 5/CM5 the same on `csi2:0` and `csi2:4` | TC358743 `set_fmt` changes only the code; width and height always come from the DV timings; field is always NONE. An ACTIVE `set_fmt` mutes and reprograms PLL, CSI and colour space. | Reported: leaving out `field:none` on the csi2 pads makes STREAMON fail with `-EPIPE` (−32) | [B-35], [C-33] |
| 8 | Set the video-node format | video node | `VIDIOC_S_FMT`: width and height equal to the timings; `UYVY` for `UYVY8_1X16`, or `BGR3` for `RGB888_1X24` on Pi 5 | — | RGB888 fourcc differs between receivers (section 8) | [C-33], [C-34] |
| 9 | Allocate buffers and start | video node | buffer allocation, STREAMON | The receiver calls `get_mbus_config` and checks the lane count against DT | `-EINVAL` "Device has requested %u data lanes, which is >%u configured in DT" → REQ-CAP-005 | [B-32], [C-16] |
| 10 | Streaming; on a source-change event | both | Recovery procedure | The driver mutes and notifies but does not reconfigure | Follow [TC358743_DRIVER.md §21](TC358743_DRIVER.md#21-recovery) | [B-39] |

Notes:

- **Order of steps 1 and 2.** Reasoning: an event raised between steps 1 and 2 would not be delivered to a subscriber that does not exist yet. Subscribing before step 1 avoids that window; the polling fallback in step 3 covers it either way. Which order the application uses is part of the PROPOSED design (NEEDS VERIFICATION, TEST-CAP-003).
- **Order of steps 6 and 7.** [C-33] enables the link before setting the pad formats, and this document follows that order. Whether the order matters is NEEDS VERIFICATION (TEST-PLT-001).
- **Pi 4 / CM4 in Media Controller mode** has no step 6 [C-36]. The register gives no tested Pi 4 Media Controller sequence. Steps 7 and 8 there are reasoning by analogy with [C-33]: NEEDS VERIFICATION (TEST-PLT-001). Whether Unicam validates the TC358743 pad format against the video-node format is also NEEDS VERIFICATION (KERNEL SOURCE INSPECTION REQUIRED; *research gap*, topic C).
- **STREAMON with no signal.** The TC358743 `s_stream` does not check signal presence and always returns 0 [B-36]. Reasoning: the application must have a successful step 4 before step 9.
- **After every probe.** The media bus code returns to RGB888_1X24 [A-09], and the driver starts with no EDID: `edid_blocks_written` is 0 after probe, so HPD stays low until an EDID is written [B-21], [A-33]. That the chip's 1 KB EDID SRAM [A-31] loses its content is a *research gap* (topic B), not a register fact. Steps 1 and 7 are therefore repeated after every boot or module load (REQ-CAP-003). What triggers the EDID write, and in which order relative to overlay load, module load and media-graph setup, is OQ-093 (OWNER DECISION REQUIRED, HARDWARE TEST REQUIRED).
- **Buffers and DMABUF** for step 9 are specified in [DMA.md](DMA.md) (REQ-DMA-001).
- **HDMI audio** *(added 2026-10-08; REQ-CAP-006)*. PROPOSED, NOT STARTED: after step 3, read "Audio present" and "Audio sampling rate" on the node that carries them (section 11) before the audio side opens ALSA at that rate; keep the step 2 `V4L2_EVENT_CTRL` subscription for the rate control, and reopen ALSA on every change [I-21]. Reasoning: the kernel does not pass the rate to ALSA by any other path [I-18] (RISK-023). The rate policy is OQ-111. Verified by TEST-AUD-001.

### Legacy-mode variant (Pi 4 / CM4 overlay default — not proposed)

Steps 1, 4 and 5 are issued on `/dev/videoN`, which forwards them to the sub-device [B-25], [C-36]. `VIDIOC_S_FMT` on the video node sets only the pixel format [C-37]. This is the path the official Raspberry Pi documentation describes [C-37]. How event subscription behaves in this mode is NEEDS VERIFICATION (section 9).

# Bench alternative: built-in EDID type 'hdmi' (CTA-861, advertises up to 1080p60 [B-24]).
# Reasoning: on a 2-lane link it advertises modes the link cannot carry [C-48]. Not for product use.
v4l2-ctl -d <S> --set-edid pad=0,type=hdmi

# Clear the EDID on pad 0 [B-24]; HPD then stays low [B-22].
# The help text shows only '--clear-edid <pad>'. Whether <pad> is given as a separate
# word (as below) or attached ('--clear-edid=0'): NEEDS VERIFICATION (OQ-101; see the notes table).
v4l2-ctl -d <S> --clear-edid 0

# Steps 4 + 5: query the source timings and apply them [C-37], [C-33].
v4l2-ctl -d <S> --set-dv-bt-timings query

# Step 6 (Pi 5 / CM5 only): enable the csi2 -> video node link [C-33].
media-ctl -d <M> -l '"csi2":4 -> "rp1-cfe-csi2_ch0":0 [1]'

# Step 7 (Pi 5 / CM5): pad formats for 1920x1080 UYVY [C-33].
media-ctl -d <M> -V '"<E>":0 [fmt:UYVY8_1X16/1920x1080 field:none colorspace:smpte170m]'
media-ctl -d <M> -V '"csi2":0 [fmt:UYVY8_1X16/1920x1080 field:none colorspace:smpte170m]'
media-ctl -d <M> -V '"csi2":4 [fmt:UYVY8_1X16/1920x1080 field:none colorspace:smpte170m]'

## 8. Pixel format (fourcc) mapping per receiver

| TC358743 media bus code | Pi 4 / CM4 Unicam pixel format | Pi 5 / CM5 CFE pixel format | Bytes in memory | Facts |
|---|---|---|---|---|
| `MEDIA_BUS_FMT_UYVY8_1X16` | `V4L2_PIX_FMT_UYVY` | `V4L2_PIX_FMT_UYVY` | — (CSI-2 data type YUV422_8B) | [C-34] |
| `MEDIA_BUS_FMT_RGB888_1X24` | `V4L2_PIX_FMT_RGB24` | `V4L2_PIX_FMT_BGR24` (`BGR3` in [C-33]) | B, G, R — on CM4, reported in an issue and explained by a Raspberry Pi engineer as blue sent first on CSI-2 | [C-34], [C-35] |

What the event means:

- The driver supports `V4L2_EVENT_SOURCE_CHANGE` and `V4L2_EVENT_CTRL` subscriptions [B-38].
- It raises `V4L2_EVENT_SOURCE_CHANGE` with `V4L2_EVENT_SRC_CH_RESOLUTION` on a sync change, or on a DE size/position change while the signal is stable, only if a sub-device node exists [B-39].
- The event carries no timings. The driver does not apply new timings itself, so the application must re-run steps 4–9 of section 6 [B-39].
- Without INT wired, events are produced from 1000 ms polling [A-30], [B-19]. RISK-013, OQ-020.
- *Research gap* (topics B and C): the CFE notification code appears to skip registered nodes, which would explain why the video node misses the event. Not a register fact; KERNEL SOURCE INSPECTION REQUIRED and HARDWARE TEST REQUIRED (TEST-CAP-003, OQ-051).

### 9.1 Control events for HDMI audio (`V4L2_EVENT_CTRL`)

*Added 2026-10-08 from research topic I* (HDMI audio required, REQ-CAP-006).

- The driver updates "Audio sampling rate" when its CBIT interrupt status reports a sample-rate change (`MASK_I_CBIT_FS`), and "Audio present" on audio lock or unlock (`MASK_I_AF_LOCK` / `MASK_I_AF_UNLOCK`). These CBIT interrupts are unmasked only while +5V / cable is detected. `tc358743_subscribe_event()` accepts `V4L2_EVENT_CTRL` (passed to `v4l2_ctrl_subdev_subscribe_event()`), so userspace can get a control-change event on a rate change and reopen the ALSA stream at the new rate [I-21].
- Without INT wired, the change reaches the control up to about 1 s late, plus I2C time [I-22] (OQ-020, OQ-111).
- The control IDs to subscribe to are 0x00981980 for "Audio sampling rate" and 0x00981981 for "Audio present" [I-20]. The subscription ioctl and the field that carries the control ID are generic V4L2 API that the source register does not quote: NEEDS VERIFICATION (KERNEL SOURCE INSPECTION REQUIRED; the PACSCORDER application is NOT STARTED).

Where to subscribe (the node that carries the controls, section 11):

| CM4, legacy mode (overlay default) | The video node carries the TC358743 controls, copied there by Unicam [I-23]. Whether control events are delivered on the video node for a copied control: NEEDS VERIFICATION (KERNEL SOURCE INSPECTION REQUIRED; HARDWARE TEST REQUIRED, TEST-AUD-001) | [I-23] |
| CM4, Media Controller mode (ADR-006, PROPOSED) | PROPOSED: the TC358743 sub-device node. Reasoning from [I-23]: Unicam copies the controls only when `mc_api` is false, so in this mode they are only on the sub-device node | [I-23], [B-18] |
| CM5 (RP1 CFE) | The TC358743 sub-device node: the controls are only there [I-23] | [I-23], [I-21] |

## 10. Enumeration caveats

- **Filtered `VIDIOC_ENUM_FMT` on Unicam (Media Controller mode).** *Research gap* (topic C, not a register fact): downstream Unicam marks `UYVY8_1X16` as `mc_skip`. As a result, `VIDIOC_ENUM_FMT` filtered by that media bus code returns nothing, even though setting UYVY with `S_FMT` works. The application must not rely on filtered `ENUM_FMT` (ADR-006 consequence). KERNEL SOURCE INSPECTION REQUIRED; OQ-046.
- **No frame-size or frame-interval enumeration on the TC358743 pad.** The driver implements neither `enum_frame_size` nor `enum_frame_interval` [B-38]. Reasoning: modes are discovered through `DV_TIMINGS_CAP`, `ENUM_DV_TIMINGS` and `QUERY_DV_TIMINGS`, all implemented [B-38].
- **Media bus codes.** `enum_mbus_code` returns exactly two codes; index 0 is RGB888_1X24 [A-09].
- **DV-timings capability.** 640–1920 × 350–1200, 13–165 MHz pixel clock; progressive, reduced blanking and custom; no interlaced [A-08], [B-26].
- **Frame rate.** Reported as an integer, so 59.94 Hz and 60 Hz sources look alike [B-28]. OQ-040.
- **TRY formats** on the TC358743 pad are not stored [B-35]. Do not use TRY to probe what the bridge accepts.

## 11. Controls

The TC358743 sub-device exposes exactly three controls [B-16]:

- `V4L2_CID_DV_RX_POWER_PRESENT`;

IDs and ranges are in [TC358743_DRIVER.md §22](TC358743_DRIVER.md#22-controls). It exposes no `V4L2_CID_LINK_FREQ` or `V4L2_CID_PIXEL_RATE` [B-16]. The consequences are in sections 14 and 15.

## 12. Buffers (summary)

- Reasoning: one 1920x1080 frame is 4,147,200 bytes in UYVY and 6,220,800 bytes in RGB888. Four buffers are about 16.6 MB and 24.9 MB [C-53].
- On Pi 4/CM4, Unicam allocates them from CMA (videobuf2-dma-contig, no IOMMU) [C-53].
- On Pi 5/CM5 the RP1 CSI nodes sit behind an IOMMU, so it is not established whether CFE buffers count against CMA [C-53] (OQ-053, OQ-061, RISK-020).
- DMABUF sharing with the encoder (REQ-DMA-001) is in [DMA.md](DMA.md).
- *(Added 2026-10-09; research topic K / OQ-116.)* How the buffer count and queue depth affect latency: section 12.2.

### 12.1 Buffer timestamps (A/V synchronisation)

*Added 2026-10-08 from research topic I* (HDMI audio required, REQ-CAP-006).

- Every Raspberry Pi CSI receiver driver in `rpi-6.18.y` — legacy/MC `bcm2835-unicam`, the upstream-style `bcm2835-unicam`, the DT-bound downstream `rp1_cfe` and the upstream `rp1-cfe` — sets `V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC` and stamps each buffer with `ktime_get_ns()` (`CLOCK_MONOTONIC`) in its frame-start interrupt [I-33]. So on CM4 and CM5 the video timestamp marks frame start.
- The audio clock is separate: the TC358743's internal audio PLL follows the HDMI source's audio clock [I-26], and ALSA reports status with a timestamp whose clock the application picks; alsa-lib 1.2.14 switches newly opened `hw` PCMs to monotonic timestamps when the kernel PCM protocol is 2.0.9 or later [I-34].
- How the frameworks of ADR-007 use the V4L2 timestamp differs by default:
  - GStreamer 1.26.2 `v4l2src` computes the buffer's age against `CLOCK_MONOTONIC`, sets PTS from the pipeline clock minus that age, and after a bad timestamp assumes a one-frame delay for the rest of the session [I-37]. In a `v4l2src` + `alsasrc` pipeline the audio clock normally becomes the pipeline clock [I-36].
  - FFmpeg 7.1's `v4l2` input passes the kernel's monotonic timestamps through by default, while its `alsa` input uses wall-clock time; without `-ts abs` or `mono2abs` the clock bases are mixed [I-38].
- Reasoning from [I-26], [I-33], [I-36], [I-37], [I-38]: audio and video are clocked independently and aligned differently by each framework, so the A/V offset and long-run drift must be measured (OQ-112, RISK-024; TEST-AUD-001, TEST-PERF-001). No measurement exists (research gap, topic I).

### 12.2 Capture latency (added 2026-10-09)

*Added 2026-10-09; research topic K / OQ-116.* The owner's target, set on 2026-10-08, is under 1 second camera-to-viewer for WebRTC viewers only; RTMP outputs are best-effort (REQ-STR-002; OQ-116 ANSWERED). This subsection covers only the capture side. The full budget is in [PERFORMANCE.md](PERFORMANCE.md) (latency budget section). Nothing has been measured (OQ-125, RISK-031).

**When a filled buffer reaches userspace:**

| Platform | Buffer completion | If no empty buffer is queued | Facts |
|---|---|---|---|
| CM4 (downstream Unicam, `drivers/media/platform/bcm2835/bcm2835-unicam.c`) | Timestamped at Frame Start (`CLOCK_MONOTONIC`) and completed only at Frame End, so a frame reaches userspace at least one frame's readout time after its first line | The frame goes to a dummy buffer and is dropped, not queued | [K-34] |
| CM5 (downstream RP1 CFE, `rp1_cfe`) | Timestamped at Frame Start and completed in the end-of-frame handler, so capture also costs about one frame's readout time | The register entry records only that CFE sets `min_queued_buffers = 1`. What CFE does with a frame when no buffer is queued: UNKNOWN — VERIFICATION REQUIRED (KERNEL SOURCE INSPECTION REQUIRED) | [K-35] |
| Pi 4 Model B / Pi 5 | Reasoning: as CM4 / CM5, because the same downstream receiver drivers bind (section 3); not stated in [K-34] or [K-35] | As CM4 / CM5 (reasoning) | [C-09], [C-29] |

- The buffer timestamp of section 12.1 therefore precedes the buffer's availability by at least one frame's readout on CM4 [K-34] and by about one frame's readout on CM5 [K-35].
- **Queues.** The V4L2 streaming-I/O specification defines the incoming and outgoing buffer queues as FIFOs, and `VIDIOC_DQBUF` returns the oldest filled buffer [K-36]. Reasoning (the second part of [K-36]): each filled capture buffer still waiting in the outgoing queue adds one frame period of latency, 33.3 ms at 30p.
- **Buffer count and queue depth.** Reasoning (Claude, from [K-34] and [K-36]; not a register fact): a consumer that dequeues each buffer as soon as it is completed leaves none waiting, so capture adds only the readout above. A consumer that falls behind adds one frame period per waiting buffer, and the backlog cannot exceed the number of allocated buffers; on CM4, once no empty buffer is queued, further frames are dropped [K-34] rather than delayed. More buffers therefore allow a longer backlog before frames are dropped; fewer buffers bound the backlog but drop frames sooner. Example: the four 1080p buffers sized in section 12 [C-53] could hold up to 4 × 33.3 ms ≈ 133 ms of backlog at 30p. The buffer count and queue policy of the live path are not decided: OQ-126 (BUILD TEST REQUIRED), RISK-032. Buffer allocation is in [DMA.md](DMA.md).
- **What `v4l2src` reports** (GStreamer is one candidate of ADR-007, OPEN). GStreamer 1.26 `v4l2src` always reports itself as live. For progressive video it reports a minimum latency of one frame duration and a maximum of buffer-pool depth × frame duration, and the pool minimum (`GST_V4L2_MIN_BUFFERS`) is 2 [K-37]. Reasoning: at 1080p30 that is 33.3 ms minimum and, with a 2-buffer pool, 66.7 ms maximum. These are the values `v4l2src` declares to the pipeline's latency query, not measurements. No register fact covers FFmpeg's `v4l2` input in this respect.
- **Assumption in the labelled budget.** Reasoning (a labelled budget, not a measurement; CORRECTED) [K-45]: the CM4 1080p30 budget counts capture readout as about 33.3 ms and assumes zero frames waiting in V4L2 or GStreamer queues, each of which would add 33.3 ms. If a later stage cannot keep up, filled capture buffers wait and each adds a frame period (reasoning from [K-36]; RISK-032; CM5 encode time: OQ-059).
- **Not covered here.** The TC358743's internal buffering latency is undocumented [K-38] ([TC358743_DRIVER.md](TC358743_DRIVER.md) §11.1; DATASHEET REQUIRED, OQ-027). Receiver frame completion side by side: [CSI_PIPELINE.md](CSI_PIPELINE.md) §7.4. Measured capture latency on CM4 and CM5: UNKNOWN — VERIFICATION REQUIRED (HARDWARE TEST REQUIRED; OQ-125, TEST-STR-002).

## 14. Why libcamera is not used

1. **Decision.** ADR-001 (ACCEPTED) chose V4L2; libcamera was among the alternatives considered.
2. **The bridge is not a camera sensor.** Its entity function is `MEDIA_ENT_F_VID_IF_BRIDGE` [B-18]. It registers no `V4L2_CID_LINK_FREQ` or `V4L2_CID_PIXEL_RATE` control [B-16], [C-19].
3. **Raspberry Pi engineers' statement.** They reported that libcamera does not support the TC358743 because it is not a raw sensor. They also reported that the main tested Pi 5 camera case is raw sensors going through the CFE [C-41].
4. **Consequence (*research gap*, topic B).** libcamera pipelines will not handle the TC358743, so PACSCORDER drives V4L2 and the Media Controller directly (sections 6 and 7).
5. **Pi 5 / CM5 format conversion.** *Research gap* (topic C): the PiSP back end through libcamera does not support this path. A community-reported alternative is a GStreamer `pispconvert` element with DMABUF caps. Whether that is usable is OQ-060.
6. **Related platform effect.** The same missing controls make the RP1 CFE fall back to a 999 Mbps D-PHY setting [C-31], [B-49] (reasoning). RISK-011, OQ-050.
